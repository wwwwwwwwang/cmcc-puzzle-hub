# 发布页类型优先流程设计

**日期：** 2026-08-05

**状态：** 已确认，待实施

**范围：** `/publish` 发布流程、创建帖子接口及相关测试

## 1. 背景与目标

当前发布页仅要求用户选择折扣和拼图编号，帖子类型由口令或二维码内容自动解析。虽然系统同时支持赠送和求助，但页面没有显式的类型入口，用户无法在操作开始时确认自己的发布意图。

本次调整将发布流程改为：

1. 选择发布类型；
2. 选择折扣和拼图编号；
3. 粘贴口令或上传二维码图片；
4. 确认预览并发布。

目标是让操作顺序符合用户心智，同时保证用户选择的类型与中国移动内容实际表达的类型一致。

## 2. 交互设计

### 2.1 类型选择

在“选择拼图”区域上方增加发布类型分段控制器，样式沿用大厅页的分段筛选：浅灰背景、选中项白底蓝字并带轻微阴影。

选项为：

- `赠送拼图`
- `求助拼图`

页面初始状态不默认选择任何类型。两个选项使用按钮语义和 `aria-pressed` 表达选中状态。

### 2.2 分步启用

- 未选择发布类型时，折扣分段控制器和拼图盘保持可见但不可操作。
- 未选择发布类型时，发布内容区域保持可见，口令输入和二维码选择继续禁用，并提示“请先选择发布类型”。
- 选择类型后，折扣和拼图盘启用。
- 选择拼图后，口令输入和二维码选择启用。
- 只有类型、拼图、至少一种有效来源、设备身份全部就绪且内容校验通过时，发布按钮才可用。

### 2.3 切换类型

用户在已经选择拼图或填写内容后切换类型时：

- 保留折扣和拼图编号；
- 保留已经填写的口令和识别出的二维码链接；
- 立即使用新选择的类型重新校验现有内容；
- 不自动修改用户选择，也不自动清空内容。

这样可以避免数据丢失，同时让类型冲突明确暴露给用户。

## 3. 类型校验

### 3.1 客户端校验

内容解析完成后，将解析得到的 `GIVE` 或 `REQUEST` 与用户选择的类型比较。

若不一致：

- 阻止发布；
- 保留全部选择和输入；
- 显示具体中文提示，例如：`选择的是求助，但内容识别为赠送，请更换内容或发布类型`。

若口令和二维码本身类型不一致，继续使用现有的双来源冲突提示。

### 3.2 服务端校验

创建帖子请求增加必填字段 `type`。服务端完成来源解析后，必须再次比较请求中的 `type` 与解析结果：

- 一致时继续发布，并使用已验证的类型写入 Redis；
- 不一致时返回 `TYPE_MISMATCH`，HTTP 状态为 `400`；
- 不允许客户端通过手工请求覆盖内容真实表达的类型。

服务端校验是数据完整性约束，客户端校验只负责及时反馈。

## 4. 组件与数据流

### 4.1 `PublishPage`

新增 `postType: PostType | null` 状态，并负责：

- 渲染类型分段控制器；
- 控制折扣选项和拼图盘是否启用；
- 将已选类型传给 `PublishPanel`。

### 4.2 `PuzzleBoard`

新增 `disabled` 属性。禁用时所有拼图按钮不可点击、不可通过键盘选择，并呈现一致的禁用视觉状态。

### 4.3 `PublishPanel`

新增 `postType: PostType | null` 属性。预览计算在现有来源解析后增加类型比较，并根据冲突生成面向用户的具体错误信息。

提交体增加：

```ts
{
  type: "GIVE" | "REQUEST";
  selection: { discount: 95 | 90 | 80; pieceNumber: number };
  sources: { command?: string; url?: string };
  visitorId: string;
}
```

### 4.4 API 与领域层

- `createPostInputSchema` 增加必填 `type` 枚举。
- `DomainErrorCode` 增加 `TYPE_MISMATCH`。
- `POST /api/posts` 在 `parseSources` 后执行类型一致性校验。
- Redis 数据结构和大厅读取接口不变，因为帖子原本已经存储 `type`。

## 5. 错误与文案

| 场景 | 提示 |
| --- | --- |
| 未选择类型 | 请先选择发布类型 |
| 未选择拼图 | 请先选择拼图 |
| 选择求助但识别为赠送 | 选择的是求助，但内容识别为赠送，请更换内容或发布类型 |
| 选择赠送但识别为求助 | 选择的是赠送，但内容识别为求助，请更换内容或发布类型 |
| 口令与二维码类型不同 | 口令与二维码对应的拼图类型不一致 |

类型冲突不清空内容，也不发送创建帖子请求。

## 6. 测试策略

### 6.1 组件测试

- 发布页初始没有选中类型。
- 未选择类型时折扣和拼图盘禁用。
- 选择类型后拼图选择启用。
- 拼图盘禁用时鼠标和键盘均不能修改选择。
- 选择类型与内容解析类型不一致时显示具体提示且发布按钮禁用。
- 切换类型后保留拼图和来源内容，并重新校验。
- 一致时创建请求包含显式 `type`。

### 6.2 领域与 API 测试

- 创建帖子输入缺少或使用非法 `type` 时校验失败。
- API 拒绝请求类型与内容解析类型不一致的发布。
- API 对一致的赠送和求助内容正常写入对应类型。

### 6.3 E2E

- 验证默认状态必须先选择类型。
- 完成一次赠送发布流程。
- 完成一次求助发布流程。
- 验证类型不一致时不发送发布请求并显示提示。
- 在 iPhone SE、iPhone 13 和 430×932 视口下无横向溢出，底部导航不遮挡操作。

## 7. 非目标

- 不允许用户手动选择的类型覆盖内容真实类型。
- 不改变大厅筛选、领取逻辑或 Redis 索引结构。
- 不增加新的发布类型。
- 不上传二维码原图。
