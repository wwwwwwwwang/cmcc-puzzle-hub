# 拼图仅二维码发布与领取设计

日期：2026-08-07

## 背景

当前一块中国移动拼图可以同时通过口令和二维码分享。口令每次复制都会生成不同的短码，但同一块拼图反复保存二维码时，解析出的链接保持不变。因此，现有按口令和完整链接分别计算摘要的去重方式，可以被“口令一帖、二维码一帖”绕过，导致同一块拼图重复占用大厅位置或重复消耗信用。

用户可能通过抽奖合法获得多块折扣和编号相同的拼图，所以不能使用“发布者 + 折扣 + 编号”作为唯一约束。业务确认每块拼图一定提供二维码，本次改为只支持二维码发布与领取，以二维码中的稳定业务凭证识别同一块拼图。

## 目标

- 发布拼图时必须上传并成功识别中国移动二维码。
- 移除口令输入、口令复制和口令唤起中国移动 APP 的流程。
- 使用二维码内层目标链接的业务凭证生成稳定去重身份。
- 同一二维码无论由哪个用户、选择哪种发布类型或附带哪些外层渠道参数，整个活动周期内都只能登记一次，帖子结束后也不能再次发布。
- 折扣和编号相同但二维码业务凭证不同的拼图可以分别发布。
- 保持现有信用、领取、求助确认、月底过期、封禁下架和并发语义。

## 非目标

- 不上传或永久保存二维码图片；浏览器仍只在本地解析图片并提交链接。
- 不调用中国移动接口反查拼图折扣或编号。
- 不识别截图中二维码以外的文字。
- 不改造现有帖子表为专用 URL 列；继续使用 `payloads` JSONB，减少数据库迁移风险。
- 不兼容新的纯口令发布。生产环境没有需要迁移的旧帖子数据。

## 发布流程

发布页保留发布类型、折扣和拼图编号三个选择步骤。“发布内容”只显示二维码上传控件，不再展示“粘贴口令 / 上传二维码”标签页。

用户选择二维码图片后，浏览器使用现有 `jsQR` 本地解析。解析成功后先进行中国移动域名和路径白名单校验，再显示“二维码链接已识别”。发布按钮仅在以下条件同时成立时可用：

1. 已登录且账号状态允许发布。
2. 已选择赠送或求助类型。
3. 已选择折扣和拼图编号。
4. 已成功识别合法二维码链接。
5. 二维码识别出的赠送/求助类型与用户选择一致。

二维码链接可以可靠识别帖子类型和稳定业务凭证，但目前不能直接解析折扣与拼图编号。因此，折扣和编号仍以用户选择为准，系统只能校验类型，不能仅凭二维码自动证明编号正确。该限制在界面中不增加说明性文案，错误选择通过发布者自检和领取反馈处理。

## 二维码规范化与唯一身份

二维码外层链接包含 `targetUrl`、渠道、页面和销售方等参数。直接哈希整条外层链接会把非业务参数计入身份，容易因参数顺序或渠道参数变化产生不同摘要。

服务端解析白名单链接后，从内层 `targetUrl` 提取：

- 活动路径，例如 `/hlwyxhdhub/act-wedrecharge/1024101716`；
- 唯一且非空的 `giveCard` 或 `requestCard` 参数；
- 由参数名确定的帖子类型 `GIVE` 或 `REQUEST`。

规范化身份按稳定格式组成：

```text
<type>:<activity-path>:<business-token>
```

身份计算忽略外层 `pageId`、`channelId`、`sellerId`、查询参数顺序，以及求助链接中的 `phone` 等非唯一业务参数。服务端仅保存该身份的 SHA-256 摘要，不向客户端或大厅列表暴露业务凭证。

相同规范化身份只能登记一次。永久身份登记、帖子创建和信用变动必须处于同一数据库事务；摘要唯一约束冲突时整次事务回滚并返回 `DUPLICATE_POST`，不得扣除信用或留下部分数据。身份登记不随帖子领取、下架、过期或封禁删除。

数据库新增永久登记表 `puzzle_identity_registry`，以规范化身份摘要为主键，并记录首次发布帖子 ID 和登记时间。现有活跃摘要表继续服务帖子生命周期和兼容既有数据库函数，但永久登记表是禁止再次发布的最终依据；释放活跃摘要时不得删除永久登记。

## 数据与 API 契约

创建帖子输入收敛为：

```ts
type CreatePostInput = {
  type: PostType;
  selection: PuzzleSelection;
  sources: {
    url: string;
  };
};
```

继续使用现有 `sources` 字段名以减少 API 改动。Schema 必须拒绝缺少 URL、空 URL、额外 `command` 字段和未知来源字段。

帖子内部统一存储：

```ts
payloads: { url: string }
availablePayloadKinds: ["URL"]
payloadHashes: [canonicalIdentityHash]
```

大厅 DTO 可继续保留 `availablePayloadKinds`，但所有新帖子都固定为 `URL`。本次不强制移除该字段，以避免无关的数据库函数和页面契约重构。

领取和助力接口成功后只返回 `{ url }`。客户端在导航前继续执行中国移动 URL 白名单校验，并设置 `Cache-Control: no-store`。二维码图片本身始终不会上传到服务端。

## 页面调整

- 发布页：移除口令标签、文本框、清除口令按钮和“将保存：口令/链接”汇总；保留二维码选择、识别、清除和错误状态。
- 大厅与帖子卡片：不再显示“口令”“口令 + 链接”来源标识；需要来源提示时统一显示“二维码”。
- 领取抽屉：只保留“打开拼图链接”主操作，移除口令复制、复制失败重试、`leadeon://` 唤起和方式切换。
- 我领取的：只展示可点击链接，不展示口令代码块。
- 我帮助的：只提供再次打开链接，不展示或复制口令。
- 我的帖子：保持状态和下架操作；来源信息统一为二维码链接。

## 生命周期与信用规则

- 赠送帖发布不扣信用，成功领取后的既有信用规则不变。
- 求助帖发布仍扣除 1 点信用；重复二维码必须在扣除前被拦截。
- 求助者手动确认收到或 24 小时自动确认后，助力者增加 1 点信用。
- 求助者确认未收到时，帖子按现有规则重新开放，原截止时间不变；原二维码摘要继续归属同一帖子，不允许另发新帖绕过。
- 帖子领取、下架、过期、封禁联动或求助流程最终结束时，按现有规则释放活跃摘要，但永久身份登记必须保留。
- 帖子过期只下架，不物理删除；月底过期规则不变。

## 错误处理

- 图片无二维码：`图片中未识别到二维码`。
- 非中国移动白名单链接：`二维码不是有效的中国移动拼图链接`。
- 二维码类型与选择不一致：沿用 `TYPE_MISMATCH`，展示实际识别类型。
- 二维码已被当前或历史帖子登记：`该二维码对应的拼图已经发布过了`。
- URL 缺失或请求仍包含口令字段：返回 `INVALID_INPUT`。
- 领取响应缺少 URL 或 URL 再校验失败：不导航，展示通用领取失败提示并保留重试入口。

## 测试策略

实现遵循测试驱动开发，先修改或新增失败测试，再写实现。

领域测试覆盖：

- 合法赠送和求助二维码解析。
- 从内层活动路径和业务参数生成稳定规范化身份。
- 外层渠道参数、参数顺序和求助 `phone` 变化不改变身份。
- `giveCard` / `requestCard` 业务凭证不同会生成不同身份。
- 空凭证、双业务参数、错误域名和错误路径继续被拒绝。
- 创建输入拒绝无二维码和 `command` 字段。

API 与仓储测试覆盖：

- 发布只传 URL 和规范化身份摘要。
- 重复摘要（包括历史已结束帖子的摘要）返回 409，并且不扣信用。
- 同折扣编号、不同摘要可以发布。
- 领取和助力只返回 URL。
- 日志不记录完整 URL、业务凭证或摘要。

组件测试覆盖：

- 发布页只有二维码上传控件，识别成功后才能发布。
- 口令标签、文本框、复制按钮和相关文案均不存在。
- 领取、我领取的和我帮助的页面只提供链接操作。
- 二维码重复错误使用新的用户文案。

E2E 覆盖：

- 仅二维码完成赠送发布和领取。
- 仅二维码完成求助发布、助力与确认。
- 无二维码不能发布。
- 重复二维码被拒绝且页面状态正确。
- 大厅筛选、信用、月底过期和账户页面流程不回退。

## 验收标准

1. 所有新帖子必须由合法中国移动二维码创建。
2. 产品界面不再出现口令输入、复制、领取或唤起入口。
3. 同一二维码业务凭证不能通过更换口令、外层参数、账号、发布选项或等待原帖结束形成第二条帖子。
4. 相同折扣和编号但不同二维码业务凭证可以正常发布。
5. 重复发布不产生帖子、不扣信用，也不留下孤立摘要。
6. 领取、助力、确认、重新开放、下架、过期和封禁流程保持原有事务语义。
7. 自动化测试、类型检查、Lint 和构建全部通过。
