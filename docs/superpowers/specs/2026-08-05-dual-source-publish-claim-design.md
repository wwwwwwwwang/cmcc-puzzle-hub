# 拼图双来源发布与领取交互设计

日期：2026-08-05

## 背景

当前发布流程将中国移动口令和二维码链接视为互斥来源，一条帖子只能保存其中一种。发布页同时展示文本框和图片按钮，但两者的主次关系不清晰；领取者也只能使用发布者当时选择的方式。

本次改动将一条帖子扩展为可同时保存口令和二维码链接。发布者至少提供一种来源；两种来源都有效时同时保存，领取者在领取前选择更适合当前设备的方式。

## 目标

- 将发布内容区改为“粘贴口令 / 上传二维码”两个标签页组成的单一输入区域。
- 标签切换时保留两边已填写或已识别的内容，并分别显示完成状态和错误状态。
- 一条帖子可保存口令、链接或两者，至少存在一种来源。
- 两种来源必须对应同一个折扣、拼图编号和帖子类型。
- 大厅只公开可用来源类型，不公开实际口令或链接。
- 领取抽屉在领取前直接提供“使用口令领取”和“使用链接领取”。
- 保留现有 24 小时 TTL、去重、禁止自领、并发领取和 5 分钟同设备幂等语义。

## 非目标

- 不上传或保存二维码图片；图片继续只在浏览器本地解析。
- 不增加中国移动 APP 内部路由，口令方式仍只调用 `leadeon://`。
- 不把 FingerprintJS 标识升级为可信认证凭证。
- 不引入第三种载荷类型或通用附件系统。

## 发布交互

发布页保留现有折扣和拼图编号选择。选中拼图后，“发布内容”区域显示两个等宽标签：

1. `粘贴口令`：文本区域接受完整中国移动分享文案或可解析口令。
2. `上传二维码`：选择本机图片并使用 jsQR 解析白名单链接。

标签切换不会清空另一标签的内容。每个标签独立维护内容、解析中状态和错误；通过解析后在标签文字旁显示完成标记。当前标签提供清除按钮，清除只影响当前来源。

内容区下方显示合并预览，例如 `8折6号 · 赠送`，并显示 `将保存：口令 + 链接`。至少一个来源有效且所有已填写来源互相一致时，发布按钮可用。

二维码解析失败、文件类型不支持、图片超过 10MB 或链接不在白名单时，错误只显示在二维码标签页，不清除已填写口令。口令解析错误同理。

## 领取交互

大厅卡片使用 `口令`、`链接` 或 `口令 + 链接` 标识可用方式，不返回真实载荷。

领取抽屉根据可用来源显示一个或两个操作按钮：

- `使用口令领取`：先请求领取接口；成功后写入剪贴板，写入成功后调用 `leadeon://`。
- `使用链接领取`：先请求领取接口；成功后导航到服务端已验证的中国移动白名单 URL。

两个按钮触发同一个原子领取操作，但前端记录用户选择并在响应后执行相应动作。请求进行中禁用两个按钮，防止重复提交。

领取接口成功后，帖子立即从大厅状态中移除，因为服务端已经消费该帖子。抽屉继续保留领取响应，便于完成跳转或在首选方式失败时使用另一种方式。

口令复制失败时不调用 `leadeon://`，而是显示规范化口令、复制重试按钮；若帖子也有链接，同时提供 `改用链接`。口令复制成功后固定显示“若未自动跳转，请手动打开中国移动 APP”和“再次唤起”。链接导航前再次在客户端执行白名单解析；若异常，则显示错误并允许改用口令。

## 领域模型

创建帖子输入从单个判别联合 `source` 改为双可选来源：

```ts
type CreatePostInput = {
  selection: PuzzleSelection;
  sources: {
    command?: string;
    url?: string;
  };
  visitorId: string;
};
```

Schema 对来源文本先执行 `trim`，要求至少存在一个非空来源。口令长度上限保持 1000，URL 长度上限保持 4096。

服务端分别使用现有 `parseCommand` 和 `parseUrl` 解析已提供来源，然后执行以下一致性检查：

- 每个来源解析出的选择必须与用户选择一致。
- 两种来源都存在时，解析出的 `type` 必须相同。
- 两种来源都存在时，解析出的折扣和拼图编号必须相同。

任一条件不满足时返回 `SELECTION_MISMATCH`，不写入 Redis。

存储模型使用显式双字段，避免为仅有两种固定来源引入通用数组：

```ts
type StoredPost = HallPostDto & {
  payloads: {
    command?: string;
    url?: string;
  };
  payloadHashes: {
    command?: string;
    url?: string;
  };
  publisherDeviceHash: string;
};

type HallPostDto = PuzzleSelection & {
  id: string;
  type: PostType;
  availablePayloadKinds: PayloadKind[];
  createdAt: string;
  expiresAt: string;
};
```

`availablePayloadKinds` 使用稳定顺序 `COMMAND`、`URL`，便于 UI 和测试得到确定结果。

## API 契约

`POST /api/posts` 接受新的 `sources` 对象。成功响应和大厅列表使用新的 `HallPostDto`，不包含 `payloads`、`payloadHashes`、`visitorId` 或 `publisherDeviceHash`。

`POST /api/posts/[id]/claim` 请求体仍只有 `visitorId`。成功响应改为：

```ts
type ClaimPostResponse = {
  payloads: {
    command?: string;
    url?: string;
  };
  idempotent: boolean;
};
```

领取接口返回该帖全部可用来源，由客户端执行领取前选择的方式。接口继续设置 `Cache-Control: no-store`。

错误码保持现有稳定集合。双来源不一致复用 `SELECTION_MISMATCH`，无需增加客户端无法处理的新错误码。

## Redis 原子语义

每个存在的规范化载荷独立计算 SHA-256 摘要，并使用现有 dedupe key 命名规则。发布 Lua 脚本在写入帖子和索引前检查所有实际来源的去重键：

- 任意去重键已存在，返回 `DUPLICATE`，不得留下另一个来源的去重键或帖子索引。
- 所有去重键均可用时，在同一脚本中写入帖子、一个或两个去重键和四类索引。
- 去重键和帖子使用相同 24 小时 TTL。

领取 Lua 脚本成功后，把完整 `payloads` 写入 5 分钟幂等回执，删除帖子及其所有来源去重键，并从全部索引移除帖子。相同设备在回执期内重试时返回相同 `payloads`；其他设备仍得到 `ALREADY_CLAIMED`。

## 兼容现有短期数据

上线时 Redis 中可能仍有旧结构 `{ payloadKind, payload, payloadHash }` 的未过期帖子。由于帖子最长存活 24 小时，读取和领取逻辑在一个 TTL 窗口内兼容旧结构，并在内存中规范化为新的 `payloads`、`payloadHashes` 和 `availablePayloadKinds`。不执行批量迁移，也不延长旧数据 TTL。

新发布只写新结构。兼容分支可在确认旧结构数据自然过期后另行移除，本次不增加自动清理任务。

## 隐私与安全

- 二维码图片不通过网络发送。
- 大厅列表只返回可用来源类型，不返回实际载荷或摘要。
- 领取响应只对成功领取或同设备幂等重试返回载荷。
- 日志不得记录完整口令、URL 查询串、原始 `visitorId` 或 Redis Token。
- 链接在发布时由服务端白名单校验，在客户端导航前再次校验。
- FingerprintJS 的匿名设备约束和可伪造边界不变，上线仍需网关 IP 或边缘限流。

## 测试策略

实现遵循测试驱动开发，每项行为先添加失败测试。

领域与 Schema 测试覆盖：

- 零来源拒绝。
- 仅口令、仅链接和双来源通过。
- 双来源类型或拼图选择不一致时拒绝。
- 规范化后生成稳定的来源顺序和摘要。

仓储和 Lua 测试覆盖：

- 单来源和双来源原子发布。
- 任一来源重复时整次发布无部分写入。
- 成功领取删除两个去重键及所有索引。
- 并发领取只有一个设备成功。
- 同设备幂等回执包含完整双来源。
- 旧存储结构在 TTL 兼容期内可列表和领取。

API 测试覆盖：

- 新建输入校验和双来源一致性。
- 大厅响应仅暴露 `availablePayloadKinds`。
- 领取成功返回一个或两个来源并设置 `no-store`。
- 自领、重复、过期、限流和服务不可用错误保持原语义。

组件与 E2E 测试覆盖：

- 标签切换保留内容，清除只影响当前来源。
- 两个来源拥有独立错误和完成状态。
- 仅一种有效来源即可发布，双来源不一致时不可发布。
- 领取按钮数量与 `availablePayloadKinds` 一致。
- 口令复制成功后才调用 `leadeon://`；失败时可重试或改用链接。
- 链接方式只导航至白名单 URL，并可在异常时改用口令。
- 仅口令、仅二维码和双来源三条完整发布领取流程。
- iPhone SE、iPhone 13 和 430x932 视口无横向溢出或控件重叠。

## 验收标准

1. 发布者可只提供口令、只上传二维码或同时提供两种来源。
2. 标签切换不丢失内容，所有错误靠近对应输入显示。
3. 不一致的双来源无法发布，Redis 不产生部分数据。
4. 大厅明确显示可用方式但不泄露载荷。
5. 双来源帖子允许领取者在领取前直接选择口令或链接。
6. 首选方式失败时，同一次成功领取可使用另一个已返回来源，无需再次请求。
7. 现有禁止自领、并发安全、幂等、TTL、限流和隐私边界不回退。
8. 自动化测试通过，并完成 Android 与 iPhone 真机剪贴板、`leadeon://` 和链接跳转验收。
