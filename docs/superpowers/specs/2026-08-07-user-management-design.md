# 用户管理与封禁设计

## 背景

现有 `/admin` 页面只展示 `PENDING` 用户，并提供通过、拒绝两个审核操作。管理员无法查看已通过、已拒绝或其他管理员账号，也无法在账号异常时限制其继续登录和参与帖子流程。

## 目标

- 将管理员入口和页面从“用户审核”升级为“用户管理”。
- 管理员可以查看全部用户，并按审核状态筛选。
- 保留待审核用户的通过、拒绝操作。
- 增加可逆的封禁、解封操作，不删除用户和历史数据。
- 封禁时原子处理该用户尚未结束的帖子，避免封禁后继续自动结算。
- 普通用户继续无法看到入口或访问 `/admin`。

## 页面与信息结构

管理员页面沿用“我的”子页面视觉：顶部保留返回按钮、标题和说明，新增状态筛选区与用户列表。列表每项显示用户名、公开 ID、信用、用户状态、管理员标记、注册时间和注册 IP；同一 IP 存在多个账号时继续显示风险提示。

筛选项包括“全部、待审核、已通过、已拒绝、已封禁”，默认展示全部用户。筛选通过 URL 查询参数 `status` 表达，服务端只接受固定枚举，非法值回退为全部。空状态文案按当前筛选条件变化。

页面顶部展示常驻“封禁影响说明”：封禁不会删除账号和历史记录；开放帖子会下架，求助帖退回托管信用；等待确认的求助会结束当前助力，未过期时按原截止时间重新开放，已过期时退款并结束；完成和过期历史不变。封禁按钮提交前使用确认对话框重复提示该影响。

## 权限与状态

`profiles.status` 新增 `BANNED`。只有管理员可调用用户列表、封禁和解封函数。管理员不能封禁自己，也不能通过管理页封禁其他管理员，以避免管理权限被普通操作误伤。

封禁仅允许作用于 `APPROVED`、`PENDING` 或 `REJECTED` 普通用户；重复封禁保持幂等。解封统一恢复为 `APPROVED`，不重复发放审核通过的 3 点种子信用。原有 `approve_user` 需拒绝直接批准 `BANNED` 用户，防止绕过解封语义。

被封禁用户登录时立即登出并看到明确提示。已有会话即使 Cookie 尚未清理，也会被现有 `getApprovedUser` 写操作门控拒绝，因为其状态不再是 `APPROVED`。

## 封禁时的帖子处理

封禁与帖子处理在单个数据库函数和事务中完成：

- `OPEN` 求助帖：退回仍处于 `HELD` 的 1 点信用，记录 `REFUND_REQUEST`，帖子改为 `EXPIRED` 并移除活跃去重记录。
- `OPEN` 赠送帖：帖子改为 `EXPIRED` 并移除活跃去重记录。
- `PENDING_CONFIRM` 求助帖：当前 `PENDING` 助力尝试改为 `REJECTED`。若原截止时间未到，帖子恢复 `OPEN` 且截止时间不变；若已过期，退回求助者托管信用并改为 `EXPIRED`。助力者不获得信用。
- `CLAIMED` 旧状态帖子：保持历史领取结果，不回滚已经完成的领取和信用流水。
- `COMPLETED`、`EXPIRED` 及其他已结束记录不变。

为避免重新开放的帖子在封禁期间继续被助力，大厅查询和领取/助力数据库函数必须排除发布者状态为 `BANNED`。这样记录仍保持已确认的原状态与截止时间，但不会对外可见或继续流转；解封后若仍未过期，可按原状态继续等待助力。

## 数据接口

新增管理员 RPC：

- `list_users(p_admin, p_status)`：返回全部或指定状态用户，并附同 IP 账号数。
- `ban_user(p_target, p_admin)`：校验权限、自封禁和管理员目标，原子封禁并处理未完成帖子。
- `unban_user(p_target, p_admin)`：将 `BANNED` 用户恢复为 `APPROVED`，不调整信用。

应用层将数据库字段映射为稳定的 `ManagedUser` 类型。服务端 action 统一解析 `targetId`，映射业务状态为中文错误或成功信息，并刷新 `/admin`、首页和账户相关路径。

## 错误处理与确认

- 未登录、非管理员、目标不存在、自封禁、目标管理员和状态不允许分别返回明确错误。
- 数据库异常不向客户端泄露内部消息，统一显示“操作失败，请稍后重试”。
- 封禁按钮必须二次确认；取消确认不提交 action。
- 页面说明和确认文案都明确展示帖子及信用影响。

## 非目标

- 不删除用户、认证账号、帖子或信用流水。
- 不支持直接编辑信用、用户名或管理员权限。
- 不增加批量操作、搜索、分页或独立审计后台。
