# 已拒绝用户重新审核设计

## 背景与目标

用户注册后处于 `PENDING`，管理员可以通过或拒绝。现有拒绝操作只把账号改为 `REJECTED`，未记录原因，也没有恢复待审核的入口；让用户重新注册会占用新用户名、丢失注册 IP 和审核痕迹，并且原合成邮箱仍会阻止使用同一用户名注册。

本次目标是保留已拒绝账号，允许管理员在用户补充资料后将其恢复为待审核，并让用户明确知道未通过原因。账号删除、用户自助申诉和完整审核历史不在本次范围内。

## 方案比较

### 方案 A：拒绝后删除并重新注册

实现直观，但会丢失用户名、注册 IP 和审核记录，还需要同时清理 Supabase Auth 与业务表。重复注册也会削弱同 IP 风险判断，因此不采用。

### 方案 B：保留账号，允许从已拒绝直接通过

改动较少，但状态流转不清晰，管理员无法区分“重新核验中”和“已拒绝”。现有通过函数还可能在状态被反复修改时重复发放初始信用，因此不采用。

### 方案 C：保留账号，先恢复待审核再处理

状态含义清楚，保留风险信息，也复用现有待审核列表和通过流程。采用此方案。

## 状态规则

审核状态只允许以下人工流转：

```text
PENDING  --拒绝--------> REJECTED
REJECTED --恢复待审核--> PENDING
PENDING  --通过--------> APPROVED
```

- `PENDING` 才能执行“通过”或“拒绝”。
- `REJECTED` 只能执行“恢复待审核”或现有“封禁”。
- 恢复待审核不发放信用。
- 首次从 `PENDING` 通过时固定发放 3 点信用。
- `APPROVED` 不允许再次执行审核通过或拒绝；账号违规使用现有封禁流程。
- `BANNED` 不允许通过审核操作恢复，只能使用现有解封流程。
- 不删除 Supabase Auth 用户或 `profiles` 记录，也不要求用户重新注册。

## 拒绝原因

在 `profiles` 增加：

- `rejection_reason text`：必填的当前拒绝原因，去除首尾空白后长度为 1 至 200 字符。
- `rejected_at timestamptz`：最近一次拒绝时间。

拒绝原因是面向用户的说明，不是内部备注。管理员输入区固定提示“该原因会在用户登录时显示，请勿填写敏感信息”。管理员列表中的已拒绝用户也展示该原因。

已有 `REJECTED` 数据使用通用原因“审核未通过，请联系管理员确认”补齐；其他状态不强制具有原因。恢复待审核时清空当前拒绝原因和拒绝时间，后续再次拒绝会写入新值。本次不新增历史表。

## 数据库与服务端

新增迁移 `0011_rejected_user_review.sql`：

1. 增加拒绝原因和拒绝时间字段并回填旧数据。
2. 重建 `list_users`，返回 `rejection_reason` 和 `rejected_at`，保留用户名、状态、IP 筛选及分页。
3. 重建 `reject_user(p_target, p_admin, p_reason)`，仅接受 `PENDING` 用户和合法原因。
4. 新增 `reopen_user_review(p_target, p_admin)`，仅允许 `REJECTED → PENDING`，并清空当前拒绝信息。
5. 收紧 `approve_user`，仅允许 `PENDING → APPROVED`；已通过保持幂等，其他状态返回 `INVALID_STATUS`。

所有函数继续在数据库内校验管理员身份、禁止操作管理员账号，并对目标用户行加锁，避免并发审核造成状态或信用重复变更。

Server Action 增加原因校验和恢复待审核操作。成功后刷新 `/admin`、`/me` 和相关登录状态依赖页面；RPC 状态继续映射为明确中文错误。

登录查询同时读取 `rejection_reason`。`REJECTED` 用户登录后立即退出会话，并显示“该账号审核未通过：{原因}”。缺失原因时使用通用提示，兼容迁移未完全生效或异常数据。

## 管理端交互

- 待审核用户点击“拒绝”后展开行内表单，不使用新的弹窗组件。
- 表单包含拒绝原因文本框、“确认拒绝”和“取消”，提交期间禁用重复操作。
- 已拒绝用户卡片展示当前拒绝原因和“恢复待审核”按钮。
- 恢复成功后用户进入待审核筛选；管理员需要再次点击“通过”或“拒绝”。
- 已拒绝用户仍可被封禁，也保留现有密码设置功能。
- 不在用户列表加入删除入口。

## 错误处理与安全

- 空原因、超长原因和无效目标在 Server Action 与数据库两层拒绝。
- React 以普通文本渲染原因，不注入 HTML。
- 非管理员、管理员自操作、操作管理员账号、错误状态和目标不存在继续返回明确错误。
- 恢复待审核和再次拒绝都不修改信用；只有合法的待审核通过事务发放 3 点信用。

## 测试与验收

- 迁移测试覆盖新字段、RPC 签名、状态限制、行锁、原因清理和信用发放条件。
- Server Action 测试覆盖原因校验、RPC 参数、恢复成功和错误映射。
- 组件测试覆盖拒绝表单展开/取消、必填和长度限制、已拒绝原因展示及恢复按钮。
- 登录测试覆盖具体拒绝原因和通用降级提示。
- 管理页查询测试覆盖新返回字段，确保搜索、IP 筛选和分页不回归。
- 完整运行类型检查、单元测试、Lint、构建和相关 E2E。

## 验收标准

1. 拒绝用户不会被删除，也无需重新注册。
2. 拒绝必须填写用户可见原因，用户登录时能看到该原因。
3. 管理员可将已拒绝用户恢复为待审核，但恢复不会自动通过或发放信用。
4. 审核通过只能从待审核状态发生，初始 3 点信用不会因反复操作重复发放。
5. 封禁、解封、密码设置、搜索、同 IP 筛选和分页保持现有行为。
